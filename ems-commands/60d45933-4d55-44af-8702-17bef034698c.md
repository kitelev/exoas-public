# Create ActionPrototype instance

Grounding for the "Create Action Instance" command (`169fa2ab`), bound to
`ems__ActionPrototype` layouts. Sibling of "Create TaskPrototype instance"
(`a6ef8fda`) — instantiates an `ems__Action` from the clicked prototype.
Also step 1 of the composite `27a37448` ("Create, Execute & Archive").

- `targetClass` → `ems__Action` (`6a99d2ca`).
- The new instance's `exo__Asset_prototype` back-link to the clicked prototype is
  written by the Universal IR `cf1ed702` (`_targetClassCondition: ems__ActionPrototype`)
  attached to the Universal Default Template singleton — same mechanism as TaskPrototype.
- **One-click (no input modal), since 2026-08-14.** `exocmd__Grounding_inputSchema`
  is deliberately absent: `CommandExecutionFlow.extractInputSchema` shows the modal
  only for a non-empty schema. ⛔ Re-adding `inputSchema` brings the modal back.
- **No stored label at all, since 2026-08-15** (`exocmd__Grounding_omitLabel: true`,
  engine v16.219.0). The instance is created WITHOUT `exo__Asset_label`; its name is
  composed at render time by the `exo__DisplayNameSpec` for `ems__Action`
  (`f39ece43`) — prototype label + the action's timestamp, e.g. «Выпить Пантокальцин
  после обеда 2026-08-15 15:54».
  - **This replaced a stored `labelTemplate`** (`$target.exo__Asset_label $nowLocal`),
    which produced the same string but FROZE it: the asset carried a literal next to
    a spec that recomputes the name on every render, and the two diverged as soon as
    either side changed. The template is gone; do not re-add it — with `omitLabel` set
    it would win and re-freeze the name.
  - **The spec is load-bearing, not decoration.** Without a spec covering the class,
    `NoteToRDFConverter` synthesises `exo__Asset_label` from the file's basename, and
    basenames are UID-canon — so a label-less action would show a bare UID. That is
    strictly worse than the `"Untitled"` this replaced. Never set `omitLabel` on a
    grounding whose target class has no `exo__DisplayNameSpec`.
  - Known and accepted (decision 2026-08-15): surfaces that read the label FROM THE
    STORE rather than through the spec — SPARQL, table sort, precondition ASK — see
    that synthesised UID. The composed name is what the UI renders.
  - The date is a preference chain, not one property (`23836bd8`):
    `endTimestamp → resolutionTimestamp → plannedEndTimestamp → startTimestamp →
    plannedStartTimestamp → createdAt`, first non-empty wins. `resolutionTimestamp`
    is the one that actually fires for this flow — the composite's Execute step
    (`ee5c36a3`) writes it, and nothing writes `endTimestamp`. `createdAt` is the
    floor so that every action has a date; measured 2026-08-15 over 130 live actions:
    resolutionTimestamp 80, plannedStart 26, plannedEnd 11, end 0, start 0, createdAt 130.
- `prefillLabelWithDate` removed with the modal — it only pre-filled a modal
  default and is dead without one.
- CLI keeps the escape hatch: an explicit `--input '{"label":"…"}'` still wins —
  `omitLabel` only changes the FALLBACK, never an explicit name.
- PropertyDefault `d9aa9bb8`: starts as `ems__EffortStatusDraft`; user taps
  "Execute" to mark it Done. No `ems__Recurring` / auto-generation (VL2).
