# WaitingCheckTask: следующая итерация (create clone + close current)

The grounding behind the `ems__WaitingCheckTask` «Следующая итерация» command
(`0f8393bc`, req `915b20b2`). A `composite` of four steps. Step 1 clones the
clicked check into the next iteration; steps 2-4 close the CURRENT (clicked)
check with an honest terminal-state lifecycle:

1. **`af871e36`** (`create_instance`) — create the next iteration cloning the
   current check (label/zone/parent/relates/body), status Backlog,
   plannedStart = tomorrow, `prevIteration` → current.
2. **`7c4213b9`** (`property_set`) — mark the CURRENT check `ems__Effort_status`
   = Done. `property_set` (not `workflow_transition`) so it is robust from any
   status (Backlog or Doing).
3. **`b2ba56b9`** (`property_set`) — set the CURRENT check
   `ems__Effort_endTimestamp` = `$nowLocal` (local timestamp).
4. **`ee5c36a3`** (`property_set`) — set the CURRENT check
   `ems__Effort_resolutionTimestamp` = `$nowLocal`.

Steps 2-4 reuse the same standard timestamp-stamping groundings the built-in
«Set Status Done» composite uses, so a closed iteration records its duration
honestly (iteration length = end − start) instead of a bare status flip
(FIX-3, полировка 2026-07-03).

Step order is create-then-close so the clone reads the current check while it is
still pristine (all `property_set` steps target the click-target, not the created
file — only `body_template` steps thread the created path). On any step failure the
composite rolls back the click-target's content.
