# Archive: set the archived flag

Grounding команды «Archive» (`archive`) — ступень 1 архивации для ассетов **без статуса**
(в первую очередь `ems__Area`).

`property_set` (тип `cf3bb923`) выставляет верхнеуровневый ключ `archived: "true"`
(`targetProperty: "archived"`, `targetValueLiteral: "true"`). Ключ входит в
unprefixed-whitelist ⇒ индексируется как триплет `exo:Asset_archived "true"` (RFC
`871c1e56`), на который смотрят оба гейта: `28f722ba` («Not archived») и `9b0fdc10`
(«Archived and not yet ontologically archived»).

**Точный инверс `ec4b6e20`** (`property_delete` того же ключа, за командой «Un-archive»).
Пара `property_set` ↔ `property_delete` симметрична и полностью обратима.

## Почему не переиспользован `eb3bb751` (`service_call archiveAsset`)

`ArchiveAssetService` (проверено по исходнику `origin/main`) делает **две** вещи: ставит
`archived: "true"` **и удаляет `aliases`**; файл не двигает. Второе действие необратимо
через «Un-archive» (`ec4b6e20` удаляет только флаг, алиасы не восстанавливает) — то есть
архивация зоны стала бы лоссовой.

Для эффортов это приемлемо (архив = терминальное состояние). Для зон архивация задумана
как **обратимая** («пока не веду, но может вернуться»), поэтому здесь взят чистый
`property_set` без побочного эффекта.

⚠ Docstring `eb3bb751` утверждает, что сервис «moves the asset to the archive folder» —
это **устаревшее** описание: в коде явное «in-place frontmatter mutation, no physical file
move». Переезд файла делает отдельная ступень 2 (`3de74a87` → `repairFolder`).
