# ems__Effort_parent

Points an `ems__Effort` at the effort it is nested under. Used for WBS-style
decomposition (project → task → action) and for the `ems__Effort_parent`
inheritance rules of the homoiconic `create-*` commands.

## Range

`exo__Property_range` = `ems__Effort` (`086f71fa-dd30-4284-90cf-e609f2a6c461`).

Widened from `ems__ParentEffort` (`17c5cf45-ce6a-4142-8d2a-65ac447f1168`) on
**2026-09-09** (founder interview, 8 forks recorded in `exoas-decisions`; subject
`ems__Task` `0e914ac3-64bd-4e13-896a-d64b3a3e8d30`, GitHub issue
`kitelev/exocortex#4220`).

Reason: an `ems__Action` created from an `ems__Task` target must nest under that
task, but `ems__Task` is not a subclass of `ems__ParentEffort` (only
`ems__Project` and `ems__Initiative` are), so `apply set-parent` on a Task
produced a `sh:class` violation. Since `ems__ParentEffort ⊂ ems__Effort`, the
widening only relaxes the shape — every value that was valid before stays valid.

Named consequence: the SHACL gate "an internal WBS node MUST be an
`ems__Project`" (decision 2026-06-20) is no longer mechanically enforced for any
class. It survives as a convention only — see the dotfiles rule
`pmbok-wbs-nested-assets`.
